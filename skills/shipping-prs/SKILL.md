license: MIT

A pull request is done when it is merged, not when it is opened. Asked only to review a pull request: report what you find and stop. Otherwise do every step yourself. Merge yourself unless the user's instructions say this kind of change waits for them; then stop after step 4 and ask.

1. **Open it** with a title naming what users get, not the mechanism, and a short body under headings holding only what the diff cannot show, inside the repository's template if it has one: the problem in a sentence or two, why it happens when that is not obvious, related issues, PRs, commits and repositories (any the change reaches) as bullet lists, testing beyond the test files (fails before and passes after, manual runs, platforms), before and after screenshots for a visible change, anything left out of scope, a `Design:` section when the change adds a module or a function other modules call or splits a file (`designing-modules`), and, when the change adds net lines to docs, rules or skills, one line starting `Why it grows:` on why it could not stay the same size. No list of changes unless a large diff needs a map. Add an attribution line only if the user's own instructions ask for one.
2. **Test it** in proportion to the change: the project's check command, plus a run of what changed. If testing, measuring or review shows the change aims at the wrong cause, or saves too little for its risk, close it with a one-line reason and fix the real cause instead (rare, and worth doing).
3. **Get every review in one round,** for every pull request, a one-line follow-up included: fresh agents review it as `reviewing-changes` says (without it, give fresh read-only agents the diff and the description, never your own list of what to check), while the repository's automated reviewer reviews the opened PR; in a public repository or someone else's, run the agents before step 1, since its push publishes the change. Wait up to about 10 minutes for the automated one; past that, go on without it.
4. **Sort every comment once.** A real bug: fix it. A nit, or a failure that has not happened and would not be catastrophic: a one-line reply. Then resolve every thread, and push all the fixes together after re-running the checks. Ask for a second automated review only when that push changed what the code does; wording fixes don't need one. Its comments are sorted the same way, once; no third round.
5. **Merge** only once `gh pr checks <number> --watch` exits 0 (on 1 a check failed, so fix it first; this holds for the browser's merge button too) and nothing is left open: where no check is required, as on a private repository on GitHub's free plan, `gh pr merge` merges a pull request whose checks are red or still running. Bound that wait just above the slowest check's usual time, read from recent runs (`gh run list -w <workflow> --json createdAt,updatedAt`), e.g. `timeout 300 gh pr checks <number> --watch` in Git Bash. When the limit passes, a run still `queued` with no jobs (`gh run view <id> --json status,jobs`) is stuck: cancel it, and once it shows `completed` run `gh run rerun <id>`, or push again, and say so in your report. If that is refused, or the new run sticks too, stop and report at once. Then delete the branch and its worktree, and update any checkout that runs the merged code.

## Gotchas

- Colin has no Copilot seat since 2 November 2026, so his repositories have no automated reviewer: the fresh agents are the whole review, and there is nothing to wait for.
- Copilot reviews only when requested: on open if the repository is set up for it, else, and for any later push, `gh pr edit <number> --add-reviewer '@copilot'` (in PowerShell a bare `@copilot` is read as a variable). The request may not show in `reviewRequests`, so before merging wait for the review itself in `gh pr view <number> --json reviews`; it takes about five minutes.
- GitHub never resolves a thread when a later commit fixes it; it only marks it outdated. List the open ones with `gh api graphql -f query='{repository(owner:"<owner>",name:"<repo>"){pullRequest(number:<n>){reviewThreads(first:100){nodes{id isResolved}}}}}'` and resolve each with `isResolved` false: `gh api graphql -f query='mutation{resolveReviewThread(input:{threadId:"<id>"}){thread{isResolved}}}'`.
- Run `gh pr merge` as a command of its own: a permission check that judges a chained command as a whole (with `sleep` or a wait) can refuse what it allows alone. `gh pr merge` can also refuse a pull request that changes `.github/workflows/` ("without `workflow` scope"): the local gh key lacks that scope. Merge with the pull request's "Squash and merge" button in a browser tool, where Colin is signed in (auto-kaizen#291, 5 Nov). Its `--delete-branch` run from another checkout removes the worktree that has the branch checked out (cli/cli#13955; a session's own worktree vanished, homelab, 13 Nov): leave the flag off and delete the branch after.
