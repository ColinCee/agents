## Off

Each job has one way per project: code several parts need (logging, tracing, a client) is one shared module they all import, never a copy, and a second way you find, yours or one already there, you merge into one with its check, in this change when small, else as its own task. Before building a tool, check, page, script or format, find what already does it (`searching-before-building`) and what the project already has (its keys, stores, CI), and say what you found; then use it with a few lines of guidance, not a wrapper script; propose dropping a tool layer the project barely uses. Logic is typed and tested; a shell script only calls one program. New tooling is the latest stable and fast: uv, ruff and ty for Python; TypeScript, Biome and Vitest for the web; one `AGENTS.md`, which `CLAUDE.md` imports, and no per-editor agent files. A practice adopted for a project's code or config (a standard, or anything Colin says is the rule from now on) ships in the same change with a CI check over every instance, a lint rule or a test, so a new one must comply; a doc line is not enforcement, and where no check can exist the pull request says so. Beyond that, guard only against failures that have happened, proven by running the guard on the real past case (the commit or input before the fix) and seeing it fail, or that would be catastrophic and irreversible. A test stays only if a plausible bug would make it fail and it passes in every environment the project's checks run in (CI, local); fix one that fails somewhere, never leave it. None restates config or pins wording, though a practice's check may pin the value the practice sets.
